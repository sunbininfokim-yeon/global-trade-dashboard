## ③ "데이터가 잘못 왔으면 학습도 잘못된 것 아닌가" — **재학습 불필요**

결론부터: **어제 발견한 ESR 버그는 학습에 영향이 없다.** 전면 재학습할 이유 없다.

이유 — 버그가 있던 곳과 학습이 쓰는 곳이 다르다.

```
[학습 경로]  NASA POWER · NOAA CPC/PSL · 각국 공식통계 · FAOSTAT
             → 직접 호출. Worker를 경유하지 않음. ESR을 쓰지 않음.

[화면 경로]  Worker /api/usda-esr  ← 버그는 여기에만 있었음
             → 아직 UI에 연결도 안 돼 있었음
```

즉 **잘못된 데이터가 학습에 들어간 적이 없다.** 버그는 "앞으로 붙일 때 터질 것"을
붙이기 전에 잡은 것이다.

### 다만 하나 확인이 필요하다

중국만 예외적으로 Worker를 경유한다:

```python
# china/labels.py, china/monthly_imports.py
COMTRADE_PROXY = "https://global-trade-dashboard.../api/comtrade"
```

`/api/comtrade`는 ESR과 **다른 핸들러**라 이번 버그와 무관하다. 다만
학습이 프로덕션 Worker에 의존하는 구조 자체가 좋지 않다 —
Worker가 죽거나 캐시가 오염되면 학습이 조용히 오염된다.

→ 오늘 할 일: 중국 파이프라인이 Comtrade를 직접 호출하도록 분리하거나,
   최소한 응답을 학습 입력으로 커밋해 재현 가능하게 만든다.

**Codex/Cursor 재학습은 필요 없다.** 대신 각 국가가 라벨 최신 연도를
`model.yaml`의 `sources.labels.updated`에 적게 하면, 인도 같은 7년 시차가
다음부터는 CI에서 자동으로 걸린다.

## ④ 소스 간 품목 매칭 로직 — 설계 (오늘 구현)

추측으로 코드를 박으면 어제 ESR에서 본 사고가 반복된다. 매칭은 **표로 만들되,
근거와 커버리지를 같이 적는다.**

### `public/data/commodity_concordance_v1.json`

```json
{
  "corn": {
    "label_ko": "옥수수",
    "codes": {
      "hs":  { "code": "1005",    "system": "HS 4자리",
               "includes": ["100510 종자용", "100590 기타"] },
      "esr": { "code": "TBD",     "system": "USDA FAS ESR",
               "source": "/api/usda-esr/commodities",
               "coverage": "미국 수출 계약만" },
      "psd": { "code": "0440000", "system": "USDA PSD",
               "coverage": "국가별 수급 밸런스" }
    },
    "combinable": false,
    "note": "HS는 종자용 포함, ESR은 미국 수출만. 합계가 서로 맞지 않으므로 더하지 않는다."
  }
}
```

### 규칙 (이게 핵심)

1. **`combinable: false`가 기본값.** 커버리지가 다른 소스를 더하지 않는다.
   미국 수출(ESR)과 전세계 양자(Comtrade)를 합치면 숫자가 거짓이 된다.
2. **우선순위로 하나를 고르고, 나머지는 툴팁에 병기.** 합산이 아니라 선택.
3. **`code: "TBD"`는 추측으로 채우지 않는다.** `/api/usda-esr/commodities`가 배포되면
   FAS가 주는 공식 목록에서 채운다.
4. 화면에 **어느 소스·기준일**인지 항상 표기.

### 왜 지금 `TBD`인가

ESR 코드 목록을 받으려면 어제 추가한 `/api/usda-esr/commodities` 라우트가
배포돼야 한다(로컬에 wrangler 없음). **PR #4 머지 → 배포 → 목록 조회 → 표 완성** 순서다.
