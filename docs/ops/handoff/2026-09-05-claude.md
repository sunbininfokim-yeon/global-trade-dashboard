### 시크릿 이름 혼선 — 정리된 결론

Cloudflare Worker(`global-trade-dashboard`)에 이미 `SUPABASE_SERVICE_ROLE_KEY` /
`SUPABASE_URL` / `RESEND_API_KEY` 가 등록돼 있었고, 오늘 그 값 그대로
**GitHub Actions repo secrets 에도 같은 이름으로 복사 완료** (운영자가 직접 함).

혼동 포인트, 다음에 또 헷갈리지 않게 기록:

- Supabase Studio는 API 키를 **두 체계**로 보여준다 —
  - 새 체계 (`Publishable and secret API keys` 탭): `sb_publishable_...` / `sb_secret_...`
  - 레거시 체계 (`Legacy anon, service_role API keys` 탭): `anon`/`service_role`, 둘 다 JWT
- 이 프로젝트의 Cloudflare `SUPABASE_SERVICE_ROLE_KEY` 시크릿에는 **새 체계의
  `sb_secret_...` 값**이 들어있다 (레거시 JWT 아님). `_worker.js`가 이미 그 값으로
  `apikey`/`Authorization: Bearer` 헤더를 써서 정상 동작 중 — Supabase의 새 체계
  키는 PostgREST 호출에 레거시 키와 동일하게 쓸 수 있어서 코드 변경 불필요했다.
- **새 시크릿을 만들 필요 없이, 있는 값을 GitHub Actions에 그대로 복사하는 걸로
  끝났다.** `auth-config.js`의 anon 키는 레거시 체계 값이라 새 체계와 무관 — 그대로 둠.
- 레거시 탭에 있던 `service_role`(JWT) 값은 이번엔 안 씀. Cloudflare에 남아있던
  `service_role_API_keys`(소문자 섞인 이름) 시크릿은 코드 어디서도 참조하지 않는
  미사용/중복 시크릿으로 확인됨 — 지울지 여부는 운영자 판단.
